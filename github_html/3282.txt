 Describe the bug

 Description

In a multi‑monitor setup, when Lively is enabled only on Monitor B, and a fullscreen application is opened on Monitor B (causing Lively to auto‑pause), the desktop on Monitor A becomes unresponsive:

Cannot left‑click to select desktop icons

Cannot open right‑click context menu

Desktop does not receive mouse input

Taskbar and normal windows still work normally

The issue disappears immediately when the fullscreen application on Monitor B is closed and Lively resumes playback.

This behavior does not appear in any existing issues on the tracker (I checked multi‑monitor related issues such as #3278 and #3235 , but none describe desktop input loss)

 Environment

Windows version: Windows 26H2

Lively version: (v2.2.1.4 BETA)

Monitor setup:

Monitor A: Lively disabled

Monitor B: Lively enabled

Arrangement: (A up, B down )

Wallpaper type on Monitor B: (WebGL)

Fullscreen application: (explorer, browsers, etc.)

 Steps to reproduce

 Use a dual‑monitor setup (A + B).

Set Windows desktop background to “Slideshow”.

Enable Lively only on Monitor B.

Open any fullscreen application on Monitor B.

Lively auto‑pauses on Monitor B (expected behavior).

Wait for slideshow to switch to the next image (or manually switch to the next wallpaper).

Try clicking on the desktop of Monitor A — the desktop becomes unresponsive (cannot select icons, cannot open right‑click menu), while taskbar and windows still work normally.

 Expected behavior

 Monitor A desktop should remain fully interactive regardless of Lively pausing on Monitor B.

 Actual Behavior

Monitor A desktop becomes unclickable:

Left‑click cannot select icons

Right‑click menu does not open

Taskbar and windows still respond normally

Issue resolves instantly when fullscreen app on Monitor B is closed and Lively resumes playback

 Screenshots/Video

 No response 

 Operating system

 Windows 11 26H2

 Wallpaper running at the time (if any)

 Fluids

 Additional context

 This appears to be an interaction between Lively’s pause/resume mechanism and Windows 26H2’s desktop input routing (Explorer/DWM).

The desktop input layer seems to be incorrectly redirected to the paused Lively desktop window on Monitor B, causing Monitor A’s desktop to lose focus until Lively resumes.

No similar issue is currently reported in the tracker (multi‑monitor issues exist, but none mention desktop input loss)
